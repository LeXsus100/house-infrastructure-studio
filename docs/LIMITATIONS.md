# Known limitations

This is the first practical local version. Its intentionally bounded areas are:

- Room creation is manual or based on selected walls; small gaps are joined with straight boundary segments and rejected when those connectors cross an existing room. It does not yet scan a large floor automatically for every possible enclosed face.
- Room categories are project-level organizational groups. They do not create nested groups or change room geometry.
- Lighting control tracing depends on explicit route endpoints and documented junction/panel correspondence groups or paired riser routes. An undocumented physical splice is intentionally reported as incomplete rather than inferred.
- Wall movement and route control-point editing are numeric. Drag transform gizmos, box selection, and vertex handles are not yet included.
- Wall-attached devices remain parametrically attached when a wall moves or resizes, preserving their BACK-face recess from the finished surface. Associated route points that lie inside the edited wall footprint are reprojected into a drywall lining; complex junction topology spanning several simultaneously edited walls may still require manual route-point adjustment.
- Junction placement can split a route and provide three ports for branches or merges. Junction boxes and electrical panels support expandable termination space plus explicit many-to-one/one-to-many correspondence groups, but the enclosure-growth estimate is schematic and not a manufacturer heat/load calculation. The route planner normalizes in-wall runs to horizontal/vertical geometry, scores connected wall paths and bounded orthogonal floor/ceiling alternatives, and automatically detours around 10 cm-expanded device envelopes; it is not a global 3D obstacle solver for arbitrary structural shapes. Configurable floor/ceiling bend radii are sampled schematic curves, not manufacturer-certified minimum bend-radius calculations. Structural-transition radii are conservatively clamped to the available wall layer. Project diagnostics can now compare coordinated multi-route cluster layouts, moving a blocker and rebuilding nearby runs when the combined conflict/bend/length score improves. The search is deliberately bounded to nearby unlocked concealed routes (up to six ranked proposals), requires explicit preview and approval, and is not an exhaustive whole-building constructability optimizer.
- Ordered floor levels, zoomable/calibrated/registered/north-oriented image blueprints, adjacent-floor wall overlays, and shared floor-transition endpoints are supported. Blueprint registration aligns one selected point per floor, while north orientation uses a user-drawn two-point arrow; it does not perform automatic image-feature matching, north detection, or perspective correction. Continuation through a transition is represented by two floor-specific route records explicitly paired as one physical sleeve lane; editing the geometry of one floor-specific route does not automatically reshape its paired route outside the riser.
- The schematic catalogue uses simple boxes, plates, cylinders, camera symbols, recognisable appliance features, and distributed staircase steps. There are no manufacturer geometry libraries or photorealistic assets.
- The Italian conductor, Ethernet termination, conduit, and fluid-identification values are documentation defaults, not an automatic legal-compliance verdict. PE yellow-green and neutral blue are treated as reserved functional identifications; Ethernet jacket, conduit, drainage, and other project-convention colours remain explicitly configurable. A qualified designer/installer must verify the applicable edition of standards and local requirements.
- The bundled English and Italian dictionaries are kept key-for-key synchronized and cover every default catalogue item plus the overview, lighting, diagnostics, and photo workflows. Free-form project content, cable identifiers, notation, technical-standard names, and manufacturer data remain exactly as entered.
- Wall scheme and current-view output are PNG only. PDF/DXF/vector export is outside this version.
- Undo/redo history is kept for the current browser session; the saved SQLite project stores the resulting state, not the full edit history.
- Each project has a dedicated `.data/projects/<project-id>/` workspace with a validated snapshot plus `assets/` and `exports/` locations. SQLite remains authoritative. Blueprint images are stored as validated image data in the project snapshot; photo-documentation bytes are stored under `assets/photos/` with normalized SQLite metadata. The current JSON backup contains photo metadata but does not package these binary photo files; ZIP project-backup packaging remains future work.
- The client bundle includes Three.js and is intentionally substantial. Code-splitting and mesh instancing can be added if profiling of unusually large residential models warrants it.
- Automated coverage focuses on critical geometry, persistence, validation, filenames, serialization, endpoint relationships, and undo/redo. Browser-level 3D gesture automation is not included.
- The packaged desktop profile currently targets 64-bit Windows with a current-user NSIS installer. macOS/Linux bundles, automatic updates, a portable mode, and code signing are not configured. The installer is unsigned and may trigger SmartScreen. It deliberately includes a Node.js runtime, trading a larger installer for compatibility with the maintained Express/SQLite persistence layer and no end-user Node.js requirement.
- The in-app branding override changes only application UI images. Windows executable and installer icons remain the neutral public icon because changing an embedded executable icon locally would invalidate a future code signature and risk publishing the private asset.
